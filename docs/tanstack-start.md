# TanStack Start and Router in this app

How this app uses TanStack Start and TanStack Router, and how it handles each documented practice that applies to it.

The [Start TanStack Query guide](https://tanstack.com/start/latest/docs/framework/react/guide/tanstack-query) was read again on 2026-10-07, when the app adopted Query.

## How the app is put together

### Build

`vite.config.ts` registers, in order: `devtools()` from `@tanstack/devtools-vite` (first, as its docs require), `tailwindcss()`, `tanstackStart()`, `viteReact()` (after Start, as required) and `nitro()` (last, as in the official `start-basic` example). Path aliases come from `tsconfig.json` through Vite 8's `resolve.tsconfigPaths`.

`tanstackStart()` adds one import-protection rule: in the client environment, an import of `serpapi`, `openai` or `js-tiktoken` fails the build. The default rule already denies `*.server.*` files there.

`bun run build` writes a Nitro `node-server` build to `.output/`. `bun run start` serves it with `node --env-file-if-exists=.env .output/server/index.mjs`.

### Router and root route

`src/router.tsx` exports `getRouter()`, which creates a new router and a new `QueryClient` on every call (one per SSR request) and registers the router's type. The client goes into router context and `setupRouterSsrQueryIntegration` connects the two, which provides the Query context and dehydrates the cache into the HTML. Router options: `context: { queryClient }`, `scrollRestoration`, `defaultPreload: "intent"`, `defaultPreloadStaleTime: 0` (Query decides freshness) and `defaultErrorComponent: RouteError`. Query's default `staleTime` is 30 seconds, so the browser does not read again what the server just rendered.

`src/routes/__root.tsx` is created with `createRootRouteWithContext<{ queryClient: QueryClient }>()` and has no `component`, so the root renders its `Outlet`. Its `shellComponent` renders the document: `<HeadContent />` in `<head>`, then in `<body>` a `ScriptOnce` that applies the stored theme before hydration, the theme provider, the command menu, the toaster, the devtools (Router and Query panels) and `<Scripts />` last. `head()` sets the shared meta tags, icons, manifest and the stylesheet (`styles.css?url`). `notFoundComponent` handles unmatched URLs.

### Routes

| Route                             | Loader                                                                                                                                                                                       | Other options                                                                    |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `/` (`src/routes/index.tsx`)      | `listModels()` and `queryClient.query(chatQueries.session())` in parallel. An LM Studio failure comes back as data; the page explains it inline.                                             | `head` (title), `headers` (`Cache-Control: private, no-store`)                   |
| `/bench` (`src/routes/bench.tsx`) | `listModels()`, `queryClient.query(benchQueries.saved())` and `queryClient.query(benchQueries.job())` in parallel. The job is read with `staleTime: 0`, so every visit sees the current run. | `beforeLoad` throws `notFound()` outside development, `head`, `pendingComponent` |

Server state lives in the Query cache. The query factories sit next to the server functions they call: `chatQueries` in `src/server/chat.ts` and `benchQueries` in `src/server/bench.ts`. Components read them with `useSuspenseQuery`, so the loader's data renders on the server and hydrates without a second request.

- **Chat:** while a turn runs, `chatQueries.status()` polls with `refetchInterval`. Its key includes the session and the turn's start time, so a new turn never starts from the last one's status. When the status shows the turn has ended, the page reads the full session once.
- **Benchmark:** the job query's `refetchInterval` is a function that polls only while a run is active or queued. The saved-runs list is invalidated when the last run of a batch ends and after Save.
- **Mutations:** each `useMutation` writes the session or job its server function returns with `setQueryData`, since the response is the full updated resource.

| ---------------------- | ---------------------- | ------ | ------------------------ | ---------- |
| `listModels`           | `src/server/models.ts` | GET    | none                     | none       |
| `getChatSession`       | `src/server/chat.ts`   | GET    | none                     | none       |

| `measureFullResponses` | `src/server/chat.ts`   | POST   | `{ turnId }`             | none       |
| `listBenchRuns`        | `src/server/bench.ts`  | GET    | none                     | `devOnly`  |
| `getBenchJob`          | `src/server/bench.ts`  | GET    | none                     | `devOnly`  |
| `saveBenchRun`         | `src/server/bench.ts`  | POST   | `saveInput`              | `devOnly`  |
| `startBenchJob`        | `src/server/bench.ts`  | POST   | `startJobInput`          | `devOnly`  |
| `queueBenchJobs`       | `src/server/bench.ts`  | POST   | array of `startJobInput` | `devOnly`  |
| `stopBenchJob`         | `src/server/bench.ts`  | POST   | none                     | `devOnly`  |

Every input is a Zod 4 schema passed straight to `.validator()`. GET serves reads; POST serves writes and `measureFullResponses`, which spends SerpApi searches. The chat, bench and model-list handlers call `chat-session.server.ts`, `bench-job.server.ts` and `agent.ts` through static imports, which the client build drops along with the handlers it replaces by RPC stubs.

`devOnly` is function middleware whose `.server()` throws unless `import.meta.env.DEV`. The app has no `src/start.ts`, so Start installs its CSRF middleware for server functions.

### Server-only code

- `*.server.ts` files: `chat-session.server.ts`, `bench-job.server.ts` and `tokens.server.ts`.
- `agent.ts` starts with `import "@tanstack/react-start/server-only"`, so import protection denies it to any client-reachable module.
- `createServerOnlyFn` wraps the plain exports of `agent.ts` that reach server-only code: `runAgentTurn`, `executeTool` and `readQueryProgress`.
- `@tanstack/react-start/server` (`getCookie`, `setCookie`, `setResponseHeader`) is imported only by `chat-session.server.ts`.
- `SERPAPI_API_KEY`, `LMSTUDIO_URL`, `LMSTUDIO_CONTEXT_LENGTH` and `LMSTUDIO_TTL_SECONDS` are read inside functions in `agent.ts`. None has a `VITE_` prefix.

## Known cost

Zod ships to the browser. The input schemas are module-scope exports of the server-function files, which the client imports; the validators themselves are stripped from the client build.

## Related TanStack libraries

- **TanStack Query** is used for the chat session, the benchmark job and the saved runs (see [Routes](#routes)). It replaced the `setInterval` loops and the code that adopted revalidated loader data in both routes.

The others are not used. Where each would fit:

- **TanStack Pacer**: an `AsyncQueuer` with concurrency 1 matches the benchmark queue in `bench-job.server.ts`, which starts queued runs one after another on a timer.
- **TanStack AI**: its `openaiCompatible` adapter talks to LM Studio and runs server tools, which overlaps the completion and tool loop in `runAgentTurn`. That loop also recovers tool calls written as text, budgets the context window and times each phase.
- **TanStack Table, Form, Store and DB**: nothing here needs them. The benchmark tables are static, the composer is one field, and state that matters lives on the server.
